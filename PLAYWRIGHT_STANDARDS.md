# Playwright Automation Standards

## Test design

- Give each test one clear business outcome; use `test.describe` for a feature or workflow.
- Use Arrange–Act–Assert and names that state observable behaviour.
- Tag targeted suites consistently (for example, `@smoke`, `@regression`, `@critical`).
- Keep tests independent: no required execution order or shared mutable state.
- Prefer API setup/teardown for expensive prerequisites when it does not bypass the behaviour under test.

## Locators

- Prefer user-facing locators: `getByRole`, `getByLabel`, `getByPlaceholder`, and `getByText`.
- For non-semantic controls, request stable `data-testid` / `data-test` attributes.
- Never use brittle XPath, CSS classes generated by a framework, or positional selectors such as `nth-child` unless unavoidable.
- Keep page-specific locators in `tests/locators`; do not scatter selectors through Page Objects or specs.

## Page Objects and fixtures

- A Page Object represents one screen or reusable component and owns meaningful actions only; its matching locator class owns selectors.
- Keep methods intention-revealing (`checkout`, `search`, `save`) rather than exposing click sequences.
- Put only genuinely common navigation/waits in `BasePage`; avoid a large generic utility class.
- Register reusable Page Objects in fixtures to keep spec setup clean.
- Keep assertions in specs by default. Page Object assertions are appropriate for a screen's canonical loaded state.

## Reliability

- Rely on Playwright's web-first assertions and auto-waiting. Do not use fixed timeouts (`waitForTimeout`).
- Assert state after actions that drive navigation, mutations, or important UI changes.
- Use `Promise.all` only when an action and an event truly start together.
- Treat retries as diagnostics, not a way to hide flaky tests; fix unstable selectors, data, or synchronization.
- Retain trace, screenshots, and video on failures as configured in `playwright.config.ts`.

## Test data and secrets

- Keep reusable non-secret data under `tests/data` and build data through factories when values must be unique.
- Do not commit credentials, tokens, reports, or `node_modules`.
- Store URLs and secrets in `.env` locally and CI secret variables in pipelines. Store local test-user data in Git-ignored `tests/secrets/users.js`, with placeholders in `users.example.js`.
- Use dedicated test accounts and clean up data created by tests when feasible.

## Reporting and CI

- Add Allure epics/features/stories only where they add searchable business context.
- Preserve `allure-results` as a CI artifact before generating the static report.
- Run a small smoke suite on pull requests and the supported cross-browser suite on scheduled/release pipelines.
- Publish reports only after the corresponding test run; protect Netlify credentials as CI secrets.

## Review checklist

- Does the test read like a user workflow and assert the business result?
- Are selectors accessible or explicitly stable?
- Is setup isolated and data safe for parallel execution?
- Will failure artifacts make the defect diagnosable?
- Is the new work documented or tagged appropriately?
